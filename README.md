# Slime Castle Card Generator

Генератор остаётся на GitHub Pages. Вход через Google и облачные данные работают через Firebase Authentication + Firestore на бесплатном Spark, без Cloud Functions и файлового хранилища.

Репозиторий публикации: [a0gzy/SlimeCardGenerator](https://github.com/a0gzy/SlimeCardGenerator). После включения Pages сайт будет доступен по адресу **https://a0gzy.github.io/SlimeCardGenerator/**.

## Возможности

- **Гость:** редактор, картинка, JSON-импорт/экспорт и существующее локальное автосохранение.
- **Участник:** прокачка своих игровых аккаунтов, загрузка в редактор, обновление, корзина и восстановление.
- **Админ:** все участники сайта, их карточки и статы, фильтр по гильдии или точному email, назначение гильдий, журнал изменений.
- **Владелец:** дополнительно выдаёт и снимает роль админа. Гильдия не даёт административных прав.
- Никакой автоматической отправки локального черновика при входе. Сохранение в облако — только по кнопке.
- Название сохранения вводить не нужно: кнопка «Сохранить аккаунт» создаёт первый аккаунт или обновляет открытый. Если ник в редакторе пустой, используется имя Google-аккаунта. Локальная генерация доступна без ника.
- Для второго игрового аккаунта есть отдельная кнопка «Ещё один аккаунт». При нескольких аккаунтах без выбранного контекста нужно сначала открыть нужный; случайной перезаписи нет. Если облачный аккаунт уже существует, но не загружался в текущий редактор, замена требует подтверждения.
- При загрузке из облака предыдущий локальный черновик сохраняется в резервную копию. При выходе текущий черновик остаётся в браузере: учитывайте это на общих компьютерах.
- Конфликт версий не перезаписывает чужие изменения: нужно загрузить актуальную версию или сохранить свой черновик как новую карточку.

### Интерфейс

Навигация и Google-вход находятся в боковом меню. Генератор, личная коллекция и разделы админки — отдельные экраны; редактор при переходах не размонтируется и не теряет черновик. На телефоне меню открывается боковой панелью.

Google-вход на GitHub Pages использует `signInWithPopup`, в том числе на iPhone/iPad. Не переключайте iOS на `signInWithRedirect`: при разных доменах сайта (`github.io`) и Firebase (`firebaseapp.com`) Safari блокирует хранилище, через которое возвращается результат, и пользователь остаётся гостем. Это ограничение описано в [рекомендациях Firebase](https://firebase.google.com/docs/auth/web/redirect-best-practices#signinwithpopup). Вход запускается непосредственно по нажатию, до перерисовки кнопки. Если окно заблокировано, нужно разрешить всплывающие окна для сайта и повторить вход; отключать защиту от межсайтового отслеживания не требуется. Из встроенного браузера мессенджера или проблемного ярлыка «Домой» следует открыть сайт в обычной вкладке Safari/Chrome.

В генераторе постоянные вкладки **Снаряжение / Слаймы / Реликвии / Артефакты / Баффы** заменяют исходный выпадающий список. Кнопка «Сохранить аккаунт» работает без формы названия. На карточке игрока видны суммарный бонус слаймов, фаза/процент пермов и сеты 2×2: **меч / броня сверху, шлем / кольцо снизу**. Каждая вещь показывает картинку и качество: Фиол (фиолетовый), Лег (золотой), Миф (красный), Фен (розовый), с сохранением отметок I/II/III. Отсутствующие предметы серые. Счётчик 3/4 означает наличие вещей, не обещание активации игрового сет-бонуса при разной редкости.

В просмотре аккаунта — компактные плитки с картинками, уровнями, звёздами, редкостью и фрагментами, разделённые по отделам. У вкладок есть клавиатурная навигация стрелками, Home и End; длинные разделы прокручиваются внутри окна. Выбор редкости и звёзд в редакторе открывает полный список вариантов, а не крошечный скролл внутри картинки.

### Слёзы и формулы прогресса

`src/cloud/progress.js` воспроизводит бонусы слаймов и пределы пермов из исходной сборки. Первая фаза — 14 пермов без ATK, HP и CritRes; после их закрытия показывается вторая фаза из этих трёх. Процент фазы — среднее процентов входящих в неё пермов, как в оригинале.

В «Баффах» расход слёз считается для 4,5% и 9% при допущении **1 слеза = 1 попытка**:

- минимум — идеальная серия нужных пермов с максимальным приростом;
- средняя оценка — число нужных пермов × `(1 − (1 − p)^30) / p`; прежнее деление на `p` не учитывало гарант;
- гарант срабатывает на 30-й капле, а любое выпадение перма сбрасывает счётчик;
- верхняя оценка — 30 × число выпадений при минимальных приростах, включая незакрытые пермы второй фазы. Предполагается, что закрытые пермы больше не выпадают. Это модель, а не обещание результата при других игровых правилах;
- запас 95% убран. Снова показаны мин./сред./макс. количества нужных пермов, а рядом — три оценки капель с золотыми значками.

Расчёт обновляется при вводе, не перерисовывая поле редактора и не сбивая его фокус.

В «Аккаунтах союза» можно одновременно использовать поиск по нику/имени/email, гильдию, минимальный бонус слаймов, набор (Астрал/Эгида/Abyss), минимальное число предметов и качество **не ниже** выбранного. Например: Abyss, 4 предмета, качество от Лег — все четыре вещи Abyss должны быть легендарными или выше; предметы разных наборов не суммируются. Если набор не выбран, достаточно одного подходящего набора.

Сортировка по бонусу работает по всей выборке, не только по первой странице. Записи без данных слаймов идут в конец и не проходят положительную минималку. Для этого клиент читает все страницы доступных администратору карточек, фильтрует и сортирует локально. Результат остаётся только в памяти до обновления/смены фильтров/выхода; «Показать ещё» не перечитывает всю базу. Это расходует чтения Firestore, но не требует миграций или новых индексов.

В списках сеты показаны компактными значками по мотивам четырёх углов вокруг центральной картинки. Углы: меч слева сверху, броня справа сверху, шлем слева снизу, кольцо справа снизу. Каждый угол имеет цвет и короткую подпись качества; недостающие вещи серые. В подробном просмотре сохранены большие раскладки 2×2.

Сет Abyss и SS-слаймы Vladaris / Balenor-Slime включены также в исходный редактор, JSON-импорт/экспорт и PNG через проверяемые преобразования `scripts/legacy-content.mjs`. Меняются только выдаваемые/собираемые копии JS. При обновлении исходной сборки несовпадение контрольных фрагментов останавливает сборку. Старые раскладки не перезаписываются; новая раскладка слаймов по умолчанию — 6×6.

### Картинки и новые сеты

Иллюстрации для просмотра аккаунтов перечислены в `src/cloud/game-assets.js`. Для новых картинок добавь файлы в `assets/`, затем укажи подмены в `src/cloud/art-overrides.js`, например:

```js
export const artOverrides = {
  'equipment/AstralSword': 'astral-sword.webp',
  'equipment/EgidaHelmet': 'egida-helmet.webp',
  'slimes/Arp': 'arp-new.png',
};
```

Картинки четырёх слотов можно заменить независимо, не меняя расположение и данные игроков. Пока используются оригинальные изображения вещей. Подмены относятся к новому просмотру; изображения исходного PNG-генератора не переписываются автоматически.

По умолчанию карточки **не публичны**: их видят только владелец и администраторы союза. Значения игровых статов вводятся пользователями, это не подтверждённые данные из игры.

## 1. Настроить Firebase

1. В своём проекте включить **Authentication → Sign-in method → Google** и указать контактный email.
2. В **Authentication → Settings → Authorized domains** добавить `a0gzy.github.io`. Для локального входа добавить `localhost` и при необходимости `127.0.0.1`. Указывается только домен, без пути `/SlimeCardGenerator/`.
3. Создать **Cloud Firestore → Standard edition**, базу `(default)`, выбрать подходящий регион. Не оставлять базу в test mode.
4. Опубликовать `firestore.rules` во вкладке **Firestore → Rules**.
5. Опубликовать индексы, включая исключение индексации большого поля `config`:

   ```powershell
   npx firebase login
   npx firebase deploy --only firestore:rules,firestore:indexes --project YOUR_PROJECT_ID
   ```

   Использовать ID именно своего проекта из web-конфигурации. Сначала дождаться готовности индексов. Публикация правил вручную не публикует индексы.

6. Проверить API restrictions Firebase Browser key в Google Cloud Console: ключ должен использоваться только с необходимыми Firebase API, не с Gemini или другими платными Google API. Не менять ограничения вслепую: проверить вход и чтение/запись после изменения. Для защиты от злоупотребления квотами следующим шагом можно подключить Firebase App Check; авторизацию и Rules он не заменяет.

Эти действия меняют реальный облачный проект — локальная сборка сама ничего туда не публикует.

## 2. Первому аккаунту выдать владельца

1. Войти на сайте через Google. Профиль появится в `users/{UID}`; UID также виден на экране «Мой аккаунт» — кнопка с именем внизу бокового меню.
2. Через **Firebase Console → Firestore → Data** вручную создать:

   - коллекция: `access`;
   - документ: **точный UID** своего аккаунта;
   - поле: `role`, тип `string`, значение `owner`.

3. Роль подхватится автоматически. Если страница была закрыта — открыть её снова.
4. Создать ваши три гильдии во вкладке «Гильдии». Во вкладке «Люди» назначать гильдии и выдавать роль `admin`.

Владельца невозможно назначить себе из браузера. Админы не могут выдавать админов и менять владельцев. Дополнительных владельцев при необходимости создаёт только доверенный оператор Firebase Console. Персонал появляется в списке после первого входа на сайт, не из полного системного списка Firebase Authentication.

## 3. Конфигурация без значений в Git

Локальный файл **`firestore`** уже исключён `.gitignore`, вместе с `.env*`, стандартными именами сервисных аккаунтов и генерируемой конфигурацией. Скрипт читает из него только шесть полей Firebase web-config. Файл с `private_key`/`service_account` сборка отклоняет. Ни весь файл, ни административные ключи в сайт не копируются.

Для GitHub Pages:

1. **GitHub → Settings → Secrets and variables → Actions → New repository secret**.
2. Имя: `FIREBASE_WEB_CONFIG`.
3. Значение: только JSON объекта `firebaseConfig` из файла `firestore`, без импортов и `const firebaseConfig =`:

   ```json
   {
     "apiKey": "YOUR_BROWSER_API_KEY",
     "authDomain": "YOUR_PROJECT.firebaseapp.com",
     "projectId": "YOUR_PROJECT_ID",
     "storageBucket": "YOUR_PROJECT.firebasestorage.app",
     "messagingSenderId": "YOUR_SENDER_ID",
     "appId": "YOUR_APP_ID"
   }
   ```

4. **Settings → Pages → Source → GitHub Actions**. После push в `main` workflow соберёт `dist/` и опубликует сайт. Можно запустить **Deploy GitHub Pages** вручную. Сам `firestore` в репозиторий добавлять не нужно.

**Важно:** секрет Actions убирает значения из исходного Git-репозитория, но НЕ скрывает Firebase web-config от посетителя. Браузер обязан получить конфигурацию; она видна в опубликованном `cloud/config.js`. Firebase web API key — публичный идентификатор проекта, а не пароль. Доступ обеспечивают Authentication и Firestore Rules. Приватный ключ service account/Admin SDK сюда никогда не нужен и не должен попадать ни в сайт, ни в web-config secret.

PR-проверки используют только demo-конфигурацию и эмулятор, без доступа к production и без production-секретов. Скрипт локального сервера не раздаёт `firestore`, `.git`, исходники или другие произвольные файлы из рабочей папки.

## Локальная разработка

Рекомендуется Node.js 24 LTS. Для эмулятора нужен Java 21+.

```powershell
npm ci
npm run dev
```

Открыть `http://127.0.0.1:5173/SlimeCardGenerator/`. Конфигурация читается из локального файла `firestore` или из переменной окружения `FIREBASE_WEB_CONFIG`. Без конфигурации гостевой генератор продолжает работать.

```powershell
npm test
npm run test:rules
npm run build
```

`npm run build` требует web-config и создаёт `dist/`; исходные `assets/` не изменяет. В `dist/` копируются только `index.html`, `assets/` и собранный модуль `cloud/` — не credentials, тесты или исходный файл `firestore`.

Для полностью локального Google-входа без настоящего аккаунта и без обращения к production:

```powershell
npm run emulators
# Во втором терминале:
npm run dev:demo
```

Открыть `http://127.0.0.1:5174/SlimeCardGenerator/`. Кнопка входа в demo запрашивает выдуманный email и использует Google credential только в Auth Emulator, не настоящий Google. Demo использует только проект `demo-slime-castle`, не читает локальный файл `firestore`. Данные эмулятора по умолчанию временные. Роль владельца для демо можно назначить через Firestore Emulator REST API с эмуляторским `Authorization: Bearer owner`; production-правила и bootstrap в Console к этому проекту не относятся.

## Модель данных и аудит

| Коллекция | Назначение | Доступ |
| --- | --- | --- |
| `users/{uid}` | Имя, email, дата регистрации и последнего входа на сайт | Сам пользователь и админы; пользователь меняет только свой профиль |
| `cards/{id}` | Владелец, название, JSON редактора, версия, даты, признак корзины | Владелец и админы |
| `guilds/{id}` | Название гильдии | Участники читают, админы создают/переименовывают |
| `memberships/{uid}` | Одна назначенная гильдия или `null` | Сам участник и админы читают, назначают только админы |
| `access/{uid}` | `member`, `admin` или `owner` | Собственная роль и админы; владелец выдаёт/снимает только `admin` |
| `audit/{id}` | Автор, действие, объект, серверное время | Читают только админы; запись только вместе с реальным изменением |

Операции с карточками, гильдиями, назначениями и ролями используют атомарный batch/transaction. Rules через `getAfter()` требуют новое соответствующее событие с `actorId == request.auth.uid`, правильным типом действия, объектом и временем `request.time`. Нельзя изменить карточку без события, подменить автора, использовать старое событие повторно, отдельно выдумать событие, исправить или удалить журнал через клиент. Карточки удаляются мягко, чтобы сохранить объект журнала; можно восстановить из корзины.

Это журнал **кто/когда/какой объект изменил**, не история всех предыдущих JSON-версий и не аудит просмотров. Обновление собственного имени/времени входа не засоряет журнал. Удаления и изменения через Firebase Console/Admin SDK обходят Rules: доверенный оператор может менять базу напрямую. Для контроля действий операторов нужен отдельный Google Cloud Audit Logs/серверный механизм.

Данные показываются страницами по 25 записей. Лимитированные запросы обязательны и в Rules. На Spark нет счета за перерасход, но достижение квот временно ограничивает облако. Чтения для проверок Rules и дополнительные запросы профилей также расходуют квоты. Автоматических резервных копий production нет: локальный JSON-экспорт полезен, но не заменяет бэкап базы.

## Как устроено расширение

В исходном репозитории доступна только production-сборка React, без `src` и `package.json` оригинального редактора. Она сохранена без правок. Новый код находится в `src/cloud/`, собирается esbuild и монтируется отдельно в `#cloud-root`.

При сборке пути из старого репозитория автоматически заменяются в копиях JS/CSS внутри `dist/assets/`. В GitHub Actions базовый путь берётся из имени репозитория, локально — `/SlimeCardGenerator/`. Для собственного домена можно задать `SITE_BASE=/`. Оригинальные файлы `assets/` не меняются.

Сохранение читает существующий JSON-черновик из `localStorage['slime_card_profile_autosave']`. Загрузка использует существующий JSON file-input React-редактора через `File`/`DataTransfer`, обновляя его настоящее состояние, без перезаписи минифицированного JS, перезагрузки страницы или попытки рисовать UI поверх чужого React root.

При обновлении оригинального генератора нужно проверить ключ `localStorage`, формат JSON, наличие `#root input[type=file][accept=".json"]` и кнопок исходного выбора раздела с префиксами классов `dropdownToggle` / `dropdownItem`: это точки интеграции. `src/cloud/editor-bridge.js` переключает настоящее состояние React через существующие обработчики, а не перерисовывает редактор. Оформление облака изолировано селектором `#cloud-root`; дополнительные стили под `body.sc-app #root` меняют только видимые панели и элементы управления редактора, не его скрытые PNG-макеты.
